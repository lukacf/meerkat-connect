**Designed acceptance case.** OB3 represents an organizational consumer with multiple people, shared agents, deployment-owned service identities, injected stores and GitOps activation. This is a host pattern, not a claim of a completed OB3 migration.

## Prepare a deployment proposal

An employee asks a shared assistant to answer questions in a support channel using a document source. The setup agents identify two independent outcomes: document service access and frontend exposure.

The host can lack a shell or permit no executable changes at runtime. Toolkit records the selected package, image/configuration/policy changes, affected tasks and missing administrator action through the host's permitted repository workflow. A PR or merge is a deployment observation, not integration readiness.

After rollout, the deployment owner attests the realized artifact and configuration. Credential and policy owners establish selected workload identity and role grants. Runtime and interaction owners acknowledge the requested bindings.

## Separate personal and service authority

A shared specialist must not fall back to its owner's personal account when a delegated request lacks permission. Each hop retains the authenticated requester or explicit service mandate and applies current source, account, destination and local permissions.

The organizational acceptance scenario includes a personal agent delegating to a shared initiative agent and then an investigator. Actual confidential-resource reads and output routes remain subject to their owners. Declared private conversations stay isolated before multi-user exposure.

This design does not promise automatic semantic information-flow tracking after permitted content has entered a shared model context. [Access control](/reference/access-control) describes the concrete guarantees.

## Inject durable storage

The application chooses its store. Toolkit's current backend is local SQLite; a cloud backend must satisfy the required admission, CAS, event/effect and fencing contracts with its actual consistency model. No BigQuery or generic cloud-store conformance is implied.

## Deliver proactively

A notification subscription binds content class, recipient audience, destination, trigger and lifetime. The outbound owner rechecks current audience before each permitted attempt. Pause or unsubscribe handles already queued output according to the binding's policy.

Shared setup work can serve several waiting tasks, but it cannot merge their authority, conversation or result destinations. Each waiter receives only its own allowed continuation and observations.
