Connect accepts portable package metadata and validates an exact selection against the host's runtime and service contracts.

## Acquisition forms

| Form | Useful for | Required checks |
| --- | --- | --- |
| Portable MCP or skill pack | Maintained service operations and setup guidance | Protocol, artifact/endpoint, auth, actual operations and host requirements |
| Native typed adapter | Explicit provider operations or domain contracts | ABI/API compatibility, account binding, policy and lifecycle |
| CLI pack | Existing command tooling | Exact executable/dependencies, literal argv, bounded output and process ownership |
| Frontend adapter | External interaction and scoped response | Transport authenticity, admission, conversation, audience and delivery |

A skill is a distribution form, not proof of service access. MCP supports tool operations but does not itself provide a frontend's people, conversation or reply contracts.

## Imported formats

`ImportedPluginManifest` and `ImportedMcpServers` parse Agent Plugins 1.0.0 metadata. Unknown top-level manifest fields produce diagnostics; invalid known fields reject. Unknown extension namespaces remain opaque. A bad MCP entry is isolated from valid siblings. Connect's namespace is `ai.rkat.toolkit`.

`ImportedMcpbManifest` parses the supported MCPB 0.3 manifest profile, preserving unresolved host/configuration requirements. It does not extract an archive, verify executable bytes or launch the described process.

`PluginRoot` anchors bounded metadata reads to a capability directory and checks containment and file type. That is a metadata-read boundary, not an execution sandbox or general artifact verifier. Placeholder expansion is literal and single-pass; imported environment/header fields are not a secret store.

## Generic-client projection

A portable MCP entry must work independently. Components that require Connect contracts, host services, package state or dependencies cannot also advertise a generic entrypoint that ignores those requirements. Unsupported clients must receive an explicit gap rather than a silently weakened integration.

The existing `setup_inspect_plugin` tool can also list a selected package directory with `{ "staged_id": "selected-plugin", "inventory": "./" }`. The agent can follow the returned `./skills` directory and unknown skill or supporting-file names, then explicitly choose public text with the existing `files` request. Inventory uses the same anchored `PluginRoot` owner as exact reads and visits one directory per call. It reads no file contents and produces no retained source reference. Selected text keeps its existing exact hashes and recovery path after the staging files are removed.

Inventory is sorted and bounded: 256 entries, 1024 UTF-8 bytes per path, 64 KiB total path bytes, and at most 15 directory components in a request. Invalid names, observed directory changes and exceeded limits refuse without partial results. Symlinks and special entries are classified without being followed or opened; an explicitly selected directory may resolve through a symlink only within the package boundary. Completion applies to that directory enumeration, not package compatibility, immutable contents or readiness. The agent still decides which files are useful and what setup is needed.

The Rust export API can copy explicitly included skill documents, supporting files and bundled executables through the anchored `PluginRoot` reader. On Unix, it snapshots file bytes and executable intent from the same opened regular file. Exported executable files use creation mode `0755`, other files `0644`, with the caller's umask preserved. Source ownership, special mode bits and group/world write permissions are not copied. An executable file in an export is still package data; exporting it grants no permission to run it.

`inspect_existing` checks executable intent as well as file contents on Unix. Its fingerprints include an optional `executable` observation. Absence in a historical fingerprint means the mode was not recorded, rather than proving the file was non-executable.

The local round-trip control covers a plain plugin with one authored stdio server, a skill and its supporting reference. A separate generic protocol consumer reads the exported standard files and uses the server after the original source is removed. This scope does not qualify Windows permissions or full Agent Plugins client conformance. Automatic whole-package discovery, skill frontmatter validation, artifact-backed Connect package realization and saved-recipe CLI export of imported guidance remain separate work.

## Host execution modes

Python and TypeScript integrations can run in a compatible host or supervised workers with isolated dependencies. Native Rust remains useful for host constraints or measured needs. Unselected integrations should remain cold metadata: no import, process or prompt cost merely because a recipe exists.

Pool only across compatible account, credential, policy and transport boundaries. One process per agent is not the default; neither is one global process for incompatible accounts. Persistent workers need explicit concurrency, result limits, cancellation and rate-limit behavior.

Frontend listeners persist independently of a current agent run. Static assets can use an existing authenticated host; they need not imply a dedicated process. Tool-call limits and frontend queue/stream limits are separate.

Browser-only hosts declare unsupported filesystem, local stdio and installer effects. They can delegate those effects to an authorized execution host. Desktop, browser and headless interfaces share role contracts, not identical privileges.

## Existing runtime discovery

After acquisition, authorized operation metadata belongs in Meerkat's exact/deferred tool catalog and search/load controls. Acquiring a missing integration is different from discovering an already available runtime tool. Avoid a mandatory proxy or another tool catalog authority.

Cached recipe data can remain useful during a registry outage. Execution depends on exact installed artifacts and current owner records, and remote health remains a current observation.
