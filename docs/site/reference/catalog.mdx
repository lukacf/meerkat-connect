`bundled_adopted_catalog()` exposes the **101 adopted local MCP profiles** from the [OSS inventory](/library/candidates). It uses ordinary package metadata and can be supplied to `DiscoveryTools::new`. Each entry names its selected operations, configuration document, exact evidence hashes and remaining limits. Its `compatible` assessment concerns the retained installed profile, not a new account's readiness or completed automatic setup.

These entries are generated from `docs/adoption/oss-inventory.json`; maintainers do not curate a second service list. A content-derived metadata version changes when the description changes. Upstream source revision, installed artifact identity and catalog metadata revision remain distinct.

Historical evidence paths refer to the private development repository and are not included in this public source export. Catalog bytes and identities are retained unchanged. Artifact publication and supported scope are stated by the current release notes, separately from those historical references. The agent still chooses the integration, and host-owned setup must realize and verify that concrete choice.

Slack and Gmail each expose two strategies in the same service record: the
adopted Activepieces read profile and the
[first-party service component](/library/slack-gmail). Instructions, operation
hints and assessments identify the relevant strategy and its own evidence.
Neither the additional strategy nor its operations increase the integration
count. The agent chooses; failure never selects the other route automatically.

The [local consumer bundle](/library/local-install) includes these same generated
bytes as `catalog.json`, alongside the exact Agno, Activepieces and services
installation inputs. Reading that file requires no package installation. Its
evidence paths still refer to historical private records; neither this public
source export nor the consumer bundle includes that verification history or the
official GitHub/Playwright executables.

## Standalone Connect metadata

The ordinary CLI now exposes `bundled_recipe_catalog()` through the shared
`RecipeInventory` before service-resource preparation. It combines the 101 adopted
records and 10 discovery records into **111 distinct metadata entries**, preserving
whole records, digests, origins and roles. List pages and exact record reads need
no service bundle, host pairing or installation. The retained historical checkpoint
covers the actual CLI with a synthetic model; its private raw report is not
included here. It does not add adopted integrations
or establish account authentication or runtime readiness.

Service connectors and agent frontends remain separate first-class plugin roles
in both setup UIs, including extensions that declare both. A frontend still needs
a compatible persistent application host; selecting or configuring a native realm
does not supply that host. This metadata addition does not change console admission
or the separately selected runtime bundle.

## Retained research recipes

These are description counts, not adopted integration counts. The product target is [at least 100 distinct adopted OSS service/system integrations](/library/adoption), usable after documented supported-host auth/configuration. This small experimental inventory is an input to that work, not the planned breadth or its completion.

## Files versus registration

Recipe files for `google-drive-api-setup/0.1.0` and `slack-mcp-setup/0.3.0` are present in the checkout but not in the current `bundled_integration_library()` registry. Presence on disk is not compiled discovery availability.

The older `bundled_discovery_catalog()` separately retains ten metadata-only research entries. Choose the intended constructor explicitly; do not add its count to the versioned library as if they were distinct supported integrations.

## Recipe contents

An `IntegrationBundle` joins real `plugin.json`, optional `mcp.json` and typed `recipes.json` inputs. Sources retain observed hashes, upstream identity, license scope and review time. Prerequisites can include developer registration, administrator approval, account selection, authentication, artifact preparation and application binding.

A guidance-only recipe can be useful before any executable selection is feasible. It cannot pass as an executable strategy by inventing a schema digest, credential binding or lifecycle receipt. Remote recipes likewise need current account and operation verification.

## Exact selection and support

Agents choose a version and strategy explicitly. A failed strategy never triggers automatic fallback, and a retained older version is not silently upgraded. Use the returned package and library digests to pin the complete investigated description.

| Assessment | Interpretation |
| --- | --- |
| `supported` | A scoped maintainer claim requiring its stated evidence |
| `compatible` | A narrower compatibility claim, not universal readiness |
| `experimental` | Investigation and development material with unfinished acceptance |
| `unavailable` | The stated path cannot currently provide its claimed scope |

Assessment metadata never overrides policy, current provider state or runtime readiness. To promote support, record the specific host/service/account profile, artifact or endpoint identity, maintainer, auth route, operations, failure cases and evidence date.

## Maintenance

Changed instructions, prerequisites, endpoint configuration or source observations require a new package version under this library's identity contract. Retain older versions for explicit migration. Check drift in dependencies, provider tools, newcomer auth and administrator requirements separately. The explicit local `scripts/check-library-update.py` command compares pinned retained artifacts, dependencies and captured schemas; its guide is `docs/adoption/LIBRARY-MAINTENANCE.md`. It reports observations and optional unapplied proposals, without approving compatibility or changing support status.

The versioned recipe inputs are the literal include list in `crates/toolkit-package/src/library.rs`. Adopted metadata comes from `crates/toolkit-package/catalog/adopted.json`, generated by `scripts/render-adopted-catalog.py`. Its `--check` mode rejects stale output or changed acceptance evidence. The [discovery API](/api/discovery) exposes the catalog selected by the host without installation.

Selected operation IDs describe the adopted donor/profile surface. Obtain actual MCP tool names and schemas from `tools/list` after connection; catalog hints do not establish active runtime bindings.
