Toolkit's architecture separates description, selection, realization and actual use. It can grow an integration library without adding mandatory dependencies or policy to raw Meerkat.

```mermaid
flowchart TB
  USER["User request"] --> AGENT["Original agent"]
  AGENT --> SETUP["Optional setup agents"]
  SETUP --> PACKAGES["toolkit-package: descriptions and exact selections"]
  PACKAGES --> DISCOVERY["Public recipe discovery"]
  SETUP --> APP["Host policy, auth and deployment owners"]
  SETUP --> STORE["Feature state and durable handoffs"]
  APP --> MOBKIT["MobKit composition"]
  MOBKIT --> NATIVE["Meerkat runtime and WorkGraph"]
  APP --> ADAPTERS["Service and frontend adapters"]
  ADAPTERS --> PROVIDER["External provider or device"]
  APP --> UI["Controlled management projections"]
```

The automatic setup path in this diagram is **designed and incomplete**. Current SDK adapters, metadata/discovery, store and UI components have narrower implemented surfaces.

## Description and selection

`toolkit-package` owns inert package/recipe types, imported metadata and exact manifest validation. `toolkit-mobkit::discovery` presents public evidence for agents. Neither chooses an integration, grants access or contacts a provider while listing descriptions.

Descriptions can be partial. Agents complete the concrete choice after investigating source and prerequisites. This avoids a hidden classification pipeline and lets a vague request, maintained recipe or custom extension follow the same conceptual path.

## Application lifecycle

`toolkit-catalog` contains the generated Toolkit acquisition lifecycle schema. Its name refers to the native DSL catalog, not a service marketplace. It records concrete work and typed observations; it does not interpret user intent or become an auth/runtime owner.

`meerkat-toolkit` contains developing request/setup/binding/continuation composition. Production activation must adopt accepted upstream owners. Historical private request-custody, registration and admission protocols are not alternative public contracts.

`toolkit-store` supplies an injected atomic persistence boundary for feature state and effects. WorkGraph and native runtime semantics remain responsible for their own work. Durable projections do not replace the canonical owners they observe.

## Execution and reuse

Python and TypeScript operations are independently consumable. They borrow selected host transports and expose explicit operation results. Frontend transports supply provider facts or one delivery attempt; the host composes admission, conversations and durable output.

The native MCP adapter realizes a selected remote service using the existing session/native execution surface. Native tools use Meerkat's existing bundle owner; MobKit forwards and composes the accepted inputs. Toolkit does not start a second runtime to make integration code convenient.

## Presentation

The UI is a controlled view over authenticated host projections. It can validate presentation consistency and preserve control occurrences. It cannot infer grants, compute canonical readiness or turn a callback rejection into an owner outcome.

## Consumer boundaries

HomeCore retains household decisions. Reachy retains device and live-domain semantics. Organizational hosts retain tenant policy, service mandates and deployment processes. They adopt shared integration components and retire duplicate generic machinery only with explicit equivalence and migration evidence.

The [role model](/concepts/roles), [package contracts](/reference/packages) and [continuation model](/reference/continuation) describe the boundaries in more detail.
