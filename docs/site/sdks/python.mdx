The distribution is `meerkat-toolkit` version `0.9.0`, requiring Python 3.11
or newer. Import concrete `meerkat_toolkit` submodules; the root package exports
no operation classes.

## Install

Install the release wheel with the optional service profile you need:

```sh
python3 -m venv .venv-toolkit
.venv-toolkit/bin/python -m pip install \
  'meerkat-toolkit[slack] @ https://github.com/lukacf/meerkat-connect/releases/download/v0.9.0/meerkat_toolkit-0.9.0-py3-none-any.whl'
```

This installs a GitHub release asset, not a package selected from PyPI. For source
development, use `.venv-toolkit/bin/python -m pip install './sdk/python[slack]'`
from the checkout root. Keep the wheel's bundled licenses and upstream notices.

| Extra | Purpose |
| --- | --- |
| `agno` | Experimental synchronous adapter for explicitly selected real Agno functions |
| `agno-mcp` | Combined SDK source profile; use the separate reviewed Agno wheel for the adopted library |
| `home-assistant`, `gmail`, `google-calendar`, `google-drive`, `slack` | Selected HTTPX/AnyIO service operations |
| `homecore-live` | Existing HomeCore live image transport |
| `telegram` | Telegram provider normalization dependency |
| `native-host` | Application composition with `meerkat-meta==0.9.0`; requires the matching SDK and Toolkit gateway |

Service extras currently require HTTPX `>=0.28.1,<0.29` and AnyIO `>=4.13,<5`. The stdlib-only Gmail formatting and base Telegram wire transport do not require those extras.

## Native application composition

The optional native classes retain the ordinary `meerkat_meta.runtime.MetaRuntime`
configuration, callback handling and lifecycle. They require a compatible
selected Meta SDK artifact and a local Toolkit gateway on POSIX. A version
constraint alone is not qualification of that artifact.

| Startup path | Class and module |
| --- | --- |
| Original-owner Restore | `host_control.ToolkitMobKitRuntime(config, selection)` |
| Fresh application | `application_runtime.ToolkitApplicationRuntime(config, preparation, finalize)` |
| Admitted replacement | `application_update.ToolkitApplicationUpdateRuntime(config, startup)` |

Import these modules under `meerkat_toolkit`. The selected input types
`HostBootstrapSelection`, `ApplicationPreparation`, `ApplicationUpdateStartup`
and `SelectedHostArtifact` live in `meerkat_toolkit.host_control`. Use the dedicated
fresh and replacement classes; passing their input types to the base runtime
does not supply their native initialization and attempt-custody behavior.

The application provides its actual gateway, persistence and source callbacks
through the existing native configuration. Fresh and replacement startup carry
the exact selected bytes; they reject a second mob definition or tool-policy
input. The async fresh finalizer accepts a `SelectedHostArtifact`, validates and
publishes through the application's existing transaction, and returns its exact
`HostBootstrapSelection`. Replacement retains the transaction's prior policy and
native expected-revision decision. The legacy `initialize_native_owner` flag is
not a fresh application path and is refused by the current ordinary-app gateway.

Await `runtime.connect()` and keep the same runtime through
`await runtime.shutdown()`. Its `host_control` property exposes that current
process's retained private client. Fresh preparation keeps the actual outcomes
on `runtime.preparation_attempt.settlement` once an attempt exists and settles.
Cancellation joins native initialization and an entered finalizer; a published
selection must survive later failure. Fresh and replacement instances cannot
start another attempt after startup has entered.

Preserve native exceptions and any retained cleanup capability. For
`GatewayStartupCleanupError`, await its `cleanup.shutdown()`; interrupted native
startup can retain the same capability as `gateway_cleanup` on the original
exception. Neither cleanup nor a private acknowledgement proves rollback,
readiness or completion of the original task.

These APIs compose an application host with the matching Toolkit gateway and
Meta SDK. The release notes identify the qualified compositions; source/build
checks do not establish every host, replacement or recovery path.
See [host composition](/guides/host-composition#native-application-lifecycle) for
the shared lifecycle, Restore reconnect rules and service/frontend boundaries.

## Supply the MCP browser callback

`meerkat_toolkit.mcp_auth` is a host-only adapter for the existing Python
MeerkatClient MCP login methods. It binds a local callback before starting
authentication, forwards completion to native auth, and closes its socket work
on settlement. Native auth retains PKCE, state, account verification, persistence
and cancellation. Rust embedding hosts use the native loopback helper instead.

The recorded Linux qualification in
`docs/verification/20261006-mcp-native-login/REPORT.md`
used published Meerkat 0.8.51 RPC and Python SDK artifacts, a synthetic loopback
issuer and `TOKIO_WORKER_THREADS=2`. It covers the loopback source recorded there,
not the later registered-HTTPS additions, and did not repin Toolkit dependencies.
The host supplies an already connected compatible client and a protected human
sign-in presenter. No ordinary browser opener, new RPC protocol or credential
store is supplied. Do not expose the adapter as an agent tool.

For cancellable request handlers, retain `McpLoginCustodian(client, target)`
under the existing host-owned step before awaiting `begin()`. It keeps one
start task and result so a later admitted request can retrieve the same handle
after the first request is cancelled. It never retries an uncertain start.
The host still authenticates and admits every invocation, including replay.

Use the returned `StartedMcpLogin.wait` for credential observation. Explicit
host shutdown calls the custodian's `close()` and joins any pending start before
cleanup. Closing a panel must not call it. A Joined result leaves cancellation
and presentation with the original custodian. Low-level `begin_mcp_login` and
explicit `observe_mcp_auth` remain available. This is in-memory transport custody,
not recovery across process loss. The full contract is in `sdk/python/MCP-AUTH.md`.

Earlier SDK framing and Toolkit-view checks used a scripted peer. The separate
released-native run exercises wrong configured-account refusal, waiter rejoin,
Started/Joined ownership, one synthetic PKCE code exchange, status and explicit
cancel. Its report retains the original startup failure and the later bounded
success. Real provider login, authenticated requester admission, protected
presentation, process-loss recovery and the complete acquisition path remain
unverified. The qualified profile is same-host loopback. Current registered-HTTPS
callback source still requires compatible native admission and host-owned routing;
it does not establish a remote/headless production journey.

## Reuse Agno functions

**Current experimental component.** The `agno` extra selects Agno `3.0.11` and jsonschema `4.26.0`. The host supplies a configured toolkit and explicitly classifies the selected operations:

```python
from agno.tools.hackernews import HackerNewsTools
from meerkat_toolkit.adapters.agno import AgnoToolkitAdapter

adapter = AgnoToolkitAdapter(
    HackerNewsTools(timeout=10),
    functions={"get_top_hackernews_stories": "read"},
)
descriptions = adapter.describe()  # Metadata only; no provider call.
```

After authorization, `adapter.invoke(name, arguments)` validates the JSON arguments and invokes the selected upstream function with Agno's Python argument conversion. It preserves bounded result values and does not interpret returned error strings as business success. Unsupported runtime injection, hooks, approval, cache, async and streaming behavior is refused. The adapter creates no Agno agent and registers no native tools.

The host retains credentials, account isolation, network configuration and toolkit lifetime. This synchronous profile supplies no hard cancellation deadline or automatic retries. An error after a write entered the invocation boundary carries an unknown write outcome. Source and installed-wheel tests exercise actual Hacker News and PubMed bodies against controlled HTTP peers; they do not establish supported host activation or adopted integration counts. The complete component contract is maintained in `sdk/python/AGNO.md`.

Install the exact artifact and runtime constraints named in `docs/adoption/AGNO-SUPPORT.md`. The [local consumer guide](/library/local-install) supplies the current installation path; earlier verification directories retain their own artifacts. No public registry publication is claimed.

Use the installed module's `profiles` and `config-help --profile hackernews`
commands before writing a configuration. The
[account prerequisites](/library/local-install#select-an-account-through-the-host)
adds `prerequisites` and `unresolved_details` for all 36 profiles. It distinguishes
public access, API keys, access tokens, passwords and explicit service
credentials, including each profile's host and account preparation. The helper
needs no credential or provider runtime and does not perform authentication.

Save a host-controlled configuration file:

```json
{
  "profile": "hackernews",
  "operations": ["get_top_hackernews_stories"],
  "config": {"timeout": 10}
}
```

Configure the MCP host to launch the installed interpreter with:

```text
-m meerkat_toolkit_agno.agno_mcp serve --config /absolute/path/hackernews.json
```

Use `check-config --config /absolute/path/hackernews.json` to validate the
nonsecret configuration before supplying any credential. Help and validation
leave credential acquisition, account verification and grants with the host.

## Prepare the client once

The host selects authentication, endpoint, hooks and network policy, then prepares the client **before sharing it**:

```python
import httpx
from meerkat_toolkit.httpx_client import prepare_httpx_client
from meerkat_toolkit.connectors.slack import SlackOperations

async def read_selected_page(host_auth, selected_channel):
    # The application has authorized this exact account and conversation.
    async with prepare_httpx_client(httpx.AsyncClient(
        base_url="https://slack.com/",
        auth=host_auth,
        trust_env=False,
    )) as client:
        slack = SlackOperations(client)
        return await slack.history_page(selected_channel, limit=15)
```

`host_auth` is supplied by the application credential owner. The example implements no OAuth or policy check. Its endpoint and network settings are explicit host choices.

`prepare_httpx_client` returns the same client and installs the retained response-cleanup hook first. Repeated preparation is idempotent. Keep hook order and auth/transport behavior stable while operations borrow the client. `require_prepared_httpx_client` validates preparation without mutating it.

Missing or reordered preparation refuses before provider entry. Most connectors raise `HttpxClientNotPrepared`, a `ValueError` with `request_attempted=False`; Drive projects this into its typed local-failure contract.

## Transport lifetime and authority

The host owns authentication, account correspondence, grants, credential refresh/revocation and eventual client closure. Library operations neither close the borrowed client nor retry automatically. Host auth, hooks and transport must preserve the selected request and must not silently replay or retarget it.

One operation deadline covers sending and reading. Deadline expiry begins cancellation and joined cleanup; arbitrary host cleanup can exceed that deadline. Cancellation after an entered write does not prove no effect.
