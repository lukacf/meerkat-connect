A frontend lets people reach an agent through an interface such as Telegram, Slack, a web app or a device. Connect's selected design supports frontend setup from both the standalone `meerkat-connect` CLI and an application's MobKit console.

The complete journey is not yet shipped or live-qualified. This guide identifies the current CLI source behavior and the intended console experience. Check [availability](/availability) for current distribution and implementation limits.

## Start with the conversation you want

For example:

```text
Let my family talk to HomeCore through Telegram.
Use our existing HomeCore host and only the people and groups it admits.
Send replies into the permitted conversation.
```

The agent investigates suitable frontend packages and the selected host's capabilities. You can name a package or repository, but you do not need to choose an implementation before describing the result.

    The agent can ask the protected terminal controls to select a supported Forge application's Console and sign in, or to select and pair with HomeCore. This keeps the original setup conversation. You do not need to choose a service/frontend mode or provide a HomeCore flag before asking.

## Choose the host as well as the realm

The **realm** selects native configuration and conversation storage. The **application host** runs the frontend, decides who may interact, routes messages and delivers replies. Selecting a realm does not create that host.

Use a compatible persistent host that can serve the requested interface. If it needs installation or deployment changes, those belong to its operator and deployment workflow. The CLI does not become a server, and `rkat` needs no Connect command or dependency.

For HomeCore, admitted messages go to the sender's own agent. There is no destination-agent selector. Other hosts may offer a fixed target, an authorized agent choice or a routing agent; setup should show only the choices that host actually supports.

## Sign in to the host and choose the permitted interaction

For a supported Forge application, select its local Console address and enter its password in the protected terminal controls, never in chat. This creates an in-memory Console session. The application must advertise frontend-management support before the agent can use its controls; sign-in alone authorizes no configuration change. This is separate from HomeCore pairing and from the frontend provider's credentials.

For HomeCore, the CLI asks for the running host address in a separate terminal prompt. Enter it there. Choose whether to remember the pairing in the OS credential store or keep it only for this process. Neither choice sends the address or pairing credentials to the model.

Follow the host's pairing method. HomeCore can send its owner a Telegram code, or accept a code issued on its protected terminal when that feature is enabled. The latter allows pairing before Telegram is available. Enter the code through the hidden terminal prompt. If its format is wrong, correct it there or enter `/quit`; Connect keeps the input hidden and sends only a valid-format entry to HomeCore. A host rejection does not cause an automatic retry. Model sign-in, HomeCore pairing and the frontend's provider credentials are separate steps.

Once authenticated, the agent reads the host's inventory before proposing changes. Discuss who may send messages, which declared groups or channels are included, how conversations stay separate, and where replies may appear. The current HomeCore path uses its declared provider group IDs; it does not discover new groups or edit sender/group declarations. Those changes need the host operator.

For a new frontend extension, the agent can investigate a repository and ask HomeCore to inspect its exact source tag and prepare a pinned proposal. Source evidence may identify a nested package path. HomeCore returns either channel choices or its supported role selections, including the daemon mode, required facades and number of voice-map entries. The agent preserves those source pins and helps you choose the configuration that fits your request. It cannot invent a role or host binding.

The host owns package eligibility, build, review and deployment. A prepared proposal is not an installation, and applied status does not establish daemon startup, live voice or delivery. Full custom-extension setup, including independent service and frontend roles, remains an end-state requirement. Its live host acceptance is [follow-up work](/roadmap), not a first-release prerequisite.

## Review the exact change

The CLI can prepare a change to an existing channel or a new extension proposal. When HomeCore supplies a review link, the terminal can show it after the agent's turn finishes. Open that exact link yourself; your browser must be paired with HomeCore independently. The page rechecks the draft's current state.

In the same CLI conversation, you can ask, "Show that change's review link again." Connect checks HomeCore's current status and can redisplay the original link for a prepared draft or a submitted request, including later attempts and failures. The host page shows current progress and any available recovery actions; opening it approves none of them. A stale draft can still be inspected. After an uncertain submission in that conversation, continue with status checks for that request.

The new standalone source also supports returning later. Choose the same realm,
ask "Check my previous HomeCore setup," and select and pair the same host when
prompted. Connect reads private request locators saved by this version of the CLI
and asks HomeCore for current status before showing any prior request. You do not
need to find a receipt or edit a recovery file. Larger histories are read in
bounded pages.

Ask to see one of those requests' review links and Connect can show its original
host-supplied link privately after another current status check. The browser still
needs its own HomeCore pairing. Recorded, applied or failed requests retain their
actual host status. A prepared draft is inspectable, but does not prove an earlier
submission failed. No previous approval or submission permission is restored, and
Connect never resubmits a request to recover progress.

Only nonsecret request references and review paths are saved. Pairing credentials,
secret-entry links and approval records are not part of this return path. Requests
from another realm or host, and requests the current host does not admit, are not
shown. This source path still needs native and live-host qualification; older CLI
runs without saved locators retain their existing receipt-based status path.

Submitting a proposal asks for a separate terminal approval showing the host and the exact change. Sign-in or pairing alone does not approve it. For HomeCore, a successful submission records an operator review request; HomeCore then owns any build, review and activation work. A Forge application returns its own command outcome; that outcome does not establish activation or message delivery.

If the host supports protected secret entry, use the private entry link and its owner confirmation. Do not put bot tokens or other secrets in the setup conversation. A stored secret is still separate from successful provider authentication.

## Check the result and keep the host running

Ask for the submitted request's status in the setup conversation. The current CLI can read HomeCore's observations, such as building, under review, activating or applied. If submission is uncertain, request status for that same change instead of submitting it again.

Before calling the frontend ready, verify that an admitted person can send a message, the host routes it to the intended agent, and a permitted reply reaches the right conversation. An applied configuration or successful build alone does not establish this. See [readiness](/concepts/readiness) for the distinction.

At the `You:` prompt, `/quit` or end-of-input ends the setup conversation. Ctrl-C requests cancellation and exit; wait for the reported outcome. It does not return to a fresh prompt in the same conversation or undo a completed host change.

After setup exits, the persistent application host keeps the activated frontend running. Exiting the CLI does not revoke HomeCore pairing or undo a submitted change. Starting the CLI again creates a new setup conversation. Ask to check previous HomeCore setup to observe the same retained requests under current host access. This restores no old workflow or approval. Use the host's controls for ongoing operation or removal.

## Manage an existing frontend

Return to `meerkat-connect` in the same realm and ask to manage the frontend.
Select the same compatible Forge application's Console and sign in through the
[protected host controls](#sign-in-to-the-host-and-choose-the-permitted-interaction).
The agent reads the application's current inventory to find its supported actions.
You can request pause, resume, disable or removal when the application offers them;
for example, "Pause the Telegram frontend" or "Resume it".

Before approving, review the exact frontend and change, including what happens to
already accepted work and pending replies. The host's policy determines whether
that work drains, is cancelled or stops. Check the submitted change's status for
any remaining work or uncertain outcome instead of repeating the submission.
A known configuration result does not by itself establish that work has settled.

For example, Reading retains queued messages while paused and lets accepted work
and replies drain. It offers removal only after the frontend is disabled and its
component has reported settlement. Those are Reading's prerequisites; another
application may offer different actions and pending-work policies.

## Packages with more than one role

A package can provide both service operations and a frontend: Slack tools plus a bot, or Reachy operations plus voice interaction. Configure and verify each role independently. Enabling a frontend does not grant its audience every service capability, and usable service tools do not prove the frontend is live. See [connectors and frontends](/concepts/roles) for their separate lifecycles.
